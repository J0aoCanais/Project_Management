Objetivo e âmbito

O cliente pediu provas de que a equipa usa LLMs de forma responsável e inovadora na versão atual do projeto. Este documento apresenta três exemplos reais, todos verificáveis no repositório Git do projeto. Cada exemplo indica o commit onde está, o que o LLM fez, o que a equipa verificou e decidiu, e como um auditor pode confirmar.

Os commits feitos com apoio de um LLM levam no histórico a marca de coautoria da ferramenta. Há duas ferramentas identificadas desta forma:

FerramentaMarca no commitCommitsDatas

Além disso, a equipa de frontend usa um prompt-padrão, o ficheiro frontend/prompt.md, que é colado no início de cada tarefa feita com um LLM.

Exemplo 1: cálculo do retorno líquido do investidor

Este é o exemplo mais detalhado. Mostra um LLM a escrever uma regra de negócio com impacto financeiro e a equipa a validá-la contra os números do cliente antes de a aceitar.

O cliente usa uma folha de cálculo para saber quanto recebe um investidor depois de impostos. A taxa depende da estrutura do investidor: uma empresa paga IRC de 19% (ou 0% com CAEP superior a 1 ano) e um particular paga IRS de 28%. Na tarefa 09 era preciso levar esta regra para a aplicação, para ser usada nas páginas de investidores, oportunidades, finanças e operações.

O trabalho está no commit 665ff89 (20/11/2026), feito com o Claude Opus 5.5. A mensagem do commit diz: "Taxas da folha do cliente (IRC 0%/19%, IRS 28%) e testes com os 3 casos ao cêntimo (npm test)." O LLM escreveu três coisas:

FicheiroLinhasConteúdo
frontend/src/lib/taxRules.ts59Taxa por estrutura do investidor e cálculo do lucro líquido, do cash-on-cash e do retorno anualizado
frontend/tests/taxRules.test.ts42Testes com os três casos da folha do cliente e três casos-limite
frontend/package.json3Comando npm test, que corre os testes no Node sem dependências extra

A validação foi feita contra a folha do cliente, ao cêntimo. Partindo de um lucro estimado de 47 037,39 €, um capital de 231 700 € e um prazo de 6 meses, os testes exigem exatamente estes valores:

InvestidorCAEPTaxaLucro líquidoCash-on-cashAnualizado
EmpresaMais de 1 ano0%47 037,39 €20,3%40,6%
EmpresaMenos de 1 ano19%38 100,28 €16,4%32,9%
ParticularMenos de 1 ano28%33 866,92 €14,6%29,2%

Há três pormenores que mostram uso responsável. O primeiro é o arredondamento. A folha corta o lucro líquido ao cêntimo (47 037,39 × 0,81 = 38 100,2859, que fica 38 100,28). Um cálculo normal com números decimais arredondaria para 38 100,29. Por isso, as contas são feitas em cêntimos e o código explica porquê, para o comportamento não ser "corrigido" mais tarde por engano.

O segundo é a forma como a lacuna foi tratada. A folha do cliente não diz que taxa paga um particular com CAEP superior a 1 ano. Em vez de inventar uma taxa, o código usa o IRS por defeito e deixa um comentário TODO: confirmar com o cliente, com um teste próprio para esse caso. A pergunta fica visível para a equipa e para quem rever o código.

O terceiro são os limites, que ficam escritos no próprio ficheiro: só se aplicam as três taxas da folha, sem derramas, tributação autónoma nem englobamento. Quem usar a função sabe o que ela não cobre. Os testes cobrem também um prejuízo (não paga imposto) e um capital ou prazo a zero (os retornos ficam a 0, sem divisão por zero).

A parte inovadora é que estes foram os primeiros testes automáticos do frontend. Usam o executor de testes que já vem com o Node (node --test), por isso não foi preciso acrescentar nenhuma biblioteca ao projeto. Na verificação de 24/11/2026, os 6 testes passaram.

Exemplo 2: a equipa reverteu trabalho do LLM fora do âmbito

Este exemplo mostra o controlo humano sobre o que o LLM produz. Nem tudo o que o LLM gerou foi aceite, mesmo estando a funcionar.

A tarefa 09 era uma tarefa de frontend. Durante o trabalho com o Claude, alguns commits alteraram também ficheiros do backend: as rotas e o schema dos contactos, o modelo de dados, os dados de exemplo da base, os testes de contactos, a documentação da API e uma migração nova da base de dados (investor_structure_and_opportunity_contact).

No mesmo dia, o autor reverteu essas alterações no commit a25a83f, com esta justificação: "O backend fica a cargo da equipa de backend. Repõe app/, migrations/, tests/, database/ e docs/ no estado do merge da ZON-01; o frontend da tarefa 09 fica igual." Foram repostos 8 ficheiros, com 173 linhas removidas. O LLM ajudou a fazer o revert, mas a decisão foi do autor.

A regra que se aplicou é que cada parte do sistema tem dono. Uma alteração ao esquema da base de dados gerada por um LLM, dentro de uma tarefa de outra área, não entrou no projeto sem passar pela equipa responsável por essa área.

Exemplo 3: prompt-padrão da equipa de frontend

Este exemplo mostra como a equipa controla o uso de LLMs em várias pessoas ao mesmo tempo, e não só numa tarefa.

O ficheiro frontend/prompt.md foi criado a 05/11/2026 (commit e26e0ed) e é colado no início de cada tarefa de frontend feita com um LLM. Define regras obrigatórias. Todos os pedidos ao servidor passam por uma única função (apiFetch), não se usa o tipo any e os componentes partilhados são reutilizados em vez de duplicados. Os dados de exemplo ficam num só ficheiro e os limites de validação ficam em src/lib/. Toda a interface fica em português de Portugal. No fim, a tarefa tem de passar no typecheck e no build.

O prompt foi mudando com o que a equipa observou. O primeiro commit de leads feito com o Copilot (08e1da9, 05/11/2026) criou os dados de exemplo em ficheiros próprios (api/fixtures/leads.ts e api/fixtures/leadSources.ts). No dia seguinte, o commit 94b4b2f juntou os dados de exemplo num só ficheiro e atualizou o prompt.md. A 09/11/2026, o commit 6b933c9 passou esse ficheiro para src/temp.tsx e voltou a atualizar o prompt, que hoje diz que "tudo o que é hard coded vive aí". Assim, os pedidos seguintes ao LLM já seguiram a regra nova.

A verificação de 24/11/2026 confirmou que as regras são cumpridas no código atual:

Regra do prompt-padrãoResultado no código
Nenhum componente chama fetch diretamenteCumprida: só src/api/client.ts o faz
Sem tipo anyCumprida: 0 ocorrências
Sem ficheiros CSS por componenteCumprida: só existe src/index.css

Limitações

Os prompts exatos de cada tarefa não estão guardados no repositório. O que existe é o prompt-padrão, as mensagens dos commits e os comentários no código. Também não é possível garantir que todos os commits feitos com LLM têm a marca de coautoria, porque a marca depende da ferramenta e de quem faz o commit.

A verificação de 24/11/2026 encontrou ainda problemas que o uso de LLMs não apanhou. O ficheiro de configuração do TypeScript tem o nome com maiúscula (Tsconfig.json), o que faz o build falhar em Linux, e 53 testes de imóveis estão desatualizados. Por isso a equipa decidiu passar a guardar o prompt, o modelo e a data de cada tarefa, e propôs ao cliente agentes que correm os testes e o build em cada pull request (Evento 1).
