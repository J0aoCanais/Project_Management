ImoVentures: AI Project Management Handbook

Regras para a equipa usar IA no projeto ImoVentures, escritas a partir do estado real do repositório (ramo miguel-frontend, commit 9cd43b8).

Estado do projeto

As regras deste handbook partem do estado atual do código, parte a parte.

Parte O que existe Onde se confirma
Autenticação Login por formulário e por JSON, logout, /api/me; utilizadores criados só pela linha de comandos app/auth/routes.py, app/cli.py
API Contactos e papéis, imóveis e zonas, todos só para o owner app/contacts, app/properties, app/zones
Base de dados Modelo v2 completo (leads, oportunidades, operações, obras, investimentos, finanças, documentos, tarefas, auditoria), mas sem API para estas entidades app/models.py, migrations/
Frontend 22 páginas; só o login, os contactos e as zonas usam a API src/App.tsx, src/api/
Dados de exemplo Usados por leads, oportunidades, operações, obras, imóveis, investidores, finanças, documentos e definições src/temp.tsx, src/api/fixtures/
Ramos por integrar Backend de leads (LEA-01) e de oportunidades (OPO-01) git branch -a

O frontend parece mais avançado do que o produto está, porque as páginas com dados de exemplo funcionam como se tivessem backend. Um caso concreto: os imóveis já têm API, mas a página de imóveis ainda usa dados de exemplo. Além disso, o investidor ainda não tem acesso a nada: recebe 403 em todas as rotas de imóveis, e o portal do investidor previsto no frontend/prompt.md não existe.

Os dados de exemplo estão organizados para facilitar a troca pelo backend real. Cada ficheiro em src/api/ devolve os dados com a mesma forma da resposta prevista e tem o comentário TODO: trocar pelo endpoint quando existir. As stores de src/api/fixtures/ simulam o servidor: respondem com 150 ms de atraso e validam com as mesmas regras de src/lib/ que os formulários usam. Assim, ligar uma página ao backend só obriga a mudar o ficheiro da API, e os componentes ficam iguais. Falta ainda decidir qual é o ramo de referência: este handbook foi escrito sobre o miguel-frontend, mas a main tem 8 commits que este ramo não tem.

Regras de utilização da IA

A IA é usada para ler código, propor alterações, escrever testes e documentação. Estas regras definem até onde vai o papel dela e onde começa a decisão da equipa.

Desde 24/11/2026 (Evento 3), o uso de ferramentas de IA está suspenso no projeto. As regras desta secção ficam válidas para quando a equipa voltar a autorizar essas ferramentas.

A IA pode Só uma pessoa decide
Ler o repositório e explicar um módulo O que entra no âmbito e com que prioridade
Propor código, testes e migrações Fazer merge e aplicar migrações
Rever um diff e apontar problemas Dar uma tarefa como concluída
Criar dados de exemplo fictícios Usar dados reais

A IA recebe os ficheiros relevantes, e cada afirmação que faz sobre o projeto indica o ficheiro de onde vem. Nas tarefas de frontend, o prompt inclui sempre o frontend/prompt.md, que já é o prompt-padrão da equipa e define a estrutura de pastas, os componentes a reutilizar, as regras de validação e a checklist final. Quem pede código à IA tem de o saber explicar na revisão. Cada commit feito com apoio de um LLM leva a marca de coautoria da ferramenta (Co-Authored-By), e o prompt, o modelo e a data de cada tarefa ficam guardados junto da tarefa.

Nunca entram num prompt:

  • o .env, palavras-passe, tokens ou cookies;
  • dados reais de clientes ou investidores (os exemplos usam emails @exemplo.pt);
  • URLs da base de dados com credenciais.

O README do projeto está desatualizado em vários pontos, por isso uma IA que o leia sem ver o código dá respostas erradas, como o endereço antigo do health. Além disso, o produto vai guardar dados pessoais e fiscais: os contactos têm NIF, morada e consentimento RGPD, e os investidores têm capital disponível e perfil de risco. Por isso, nenhum dado real entra num prompt, nem para testar uma validação.

Workflow

Com este workflow, cada alteração feita com IA é pequena e passa pelos testes e pela revisão de outra pessoa antes de entrar na main.

Fase O que se faz Quem
Preparar Escrever o objetivo numa frase, ligado ao requisito; dar à IA os ficheiros e o prompt-padrão Autor
Planear A IA lê o código e diz o que vai reutilizar e alterar IA, aprovado pelo autor
Implementar Diff pequeno num ramo próprio (como CON-01 ou ZON-01) IA e autor
Verificar pytest, npm test, npm run typecheck, npm run build Autor
Rever e fechar Revisão do PR, atualização do README e docs/, registo do prompt Outra pessoa e autor

A equipa já trabalha com um ramo por tarefa, com códigos como CON-01, LEA-01, OPO-01 e ZON-01, e junta o trabalho por pull requests no GitHub. O workflow com IA usa esta mesma prática. No frontend, a checklist no fim do frontend/prompt.md funciona como lista de verificação do PR e pede um resumo dos componentes criados, dos componentes alterados e das diferenças face ao mockup. A IA pode redigir esse resumo, mas o autor confirma-o. A verificação corre em Linux ou no Docker, porque o erro do Tsconfig.json passou despercebido no Windows. Enquanto a IA estiver suspensa, o autor planeia e implementa sozinho, e a revisão de outra pessoa passa a ser obrigatória em todos os PRs, mesmo nos pequenos.

Requisitos e testes

Um requisito só está cumprido se houver um teste que o prove.

Cada requisito tem um ID, uma frase verificável e um teste que só pode falhar por esse motivo. No projeto, o test_add_invalid_role_id passa por causa de um campo desconhecido no pedido. Sem esse campo, a API aceita um papel que não existe e responde 201.

Conjunto de testes Resultado nesta análise
tests/test_auth.py Passam todos
tests/test_contacts.py Passam todos
tests/test_zones.py Passam todos
tests/test_properties.py 53 falham: os testes não enviam os campos que passaram a ser obrigatórios no imóvel
frontend/tests/taxRules.test.ts 6 passam
npm run typecheck e npm run build Falham em Linux por causa do nome Tsconfig.json; com tsconfig.json passam

Uma tarefa só está feita quando está na main, tem um teste que falhava antes, passa os testes de autorização (anónimo, investor e owner), passa no typecheck e no build, e tem o PR aprovado por outra pessoa.

Os testes de backend seguem um padrão que vale a pena manter. O tests/conftest.py cria uma base _test nova em cada execução e dá três clientes: um owner, um investor e um anónimo. Cada ficheiro testa primeiro que o anónimo e o investor são bloqueados e só depois o comportamento da rota. Há também testes que registam defeitos conhecidos com a marca KNOWN-ISSUE, como o imóvel apagado que continua visível e a ordenação da pesquisa que é ignorada. Cada um destes testes deve dar origem a um requisito para corrigir o defeito. No frontend só as regras de impostos têm testes. As outras regras de src/lib/ são funções simples, sem dependências, e por isso são um bom ponto de partida para a IA gerar testes.

Qualidade do código

O frontend/prompt.md já define as regras de código do frontend. Verificámos no código se estão a ser cumpridas; o resultado orienta o que a IA deve corrigir ou evitar.

Regra Estado
Todos os pedidos passam por apiFetch, nunca por fetch num componente Cumprida
Sem any no TypeScript Cumprida
Sem CSS por componente, só Tailwind e src/index.css Cumprida
Dados de exemplo só em src/temp.tsx Cumprida: as stores de src/api/fixtures/ leem de lá
Listas com quatro estados (a carregar, erro, vazio, com dados) Cumprida nas páginas de dados
Dinheiro, datas e percentagens por src/lib/format.ts Duas percentagens formatadas à mão em OperationDetailContent.tsx
Componentes com menos de ~150 linhas 5 componentes acima disso, por exemplo WorkDetailPage.tsx

No backend, o padrão a seguir é o de app/contacts/routes.py: validação com Marshmallow, campos desconhecidos recusados, rollback em caso de erro e registos apagados filtrados na própria query. A rota de detalhe do imóvel não segue este último ponto e devolve imóveis apagados.

Há dois pontos do backend que a IA não deve copiar como padrão. Em app/contacts/routes.py, a verificação if roles is None nunca é verdadeira, porque a consulta devolve uma lista. Por isso, um papel inexistente é ignorado em silêncio em vez de dar erro. Depois, as mensagens de erro da API estão em inglês (por exemplo, "Contact not found"), enquanto a interface está toda em português de Portugal. No frontend, o build gera um ficheiro JavaScript de 587 kB e o Vite avisa que passa dos 500 kB. Não é urgente, mas fica registado para quando o número de páginas crescer.

Segurança

A base de segurança está feita. A IA não a pode enfraquecer, e qualquer alteração a estes pontos precisa de revisão explícita.

Proteção Onde está
Palavras-passe com Argon2; mínimo de 12 caracteres na criação app/security.py, app/cli.py
Login limitado a 5 tentativas por minuto e com a mesma mensagem para email ou palavra-passe errados app/auth/routes.py
Sessão limpa no login, cookie HttpOnly e SameSite=Lax, Secure em produção, 8 horas app/auth/routes.py, app/config.py
CSRF em todos os pedidos que alteram dados app/extensions.py, src/api/client.ts
Rotas privadas por omissão; públicas só as listadas app/security.py

Quando o email não existe, o login verifica na mesma uma palavra-passe fictícia, para que o tempo de resposta não revele que contas existem. O utilizador é lido da base de dados em cada pedido, por isso um utilizador apagado perde a sessão de imediato. As páginas privadas são enviadas com Cache-Control: no-store, para o botão "Retroceder" não as mostrar depois do logout. O limite de tentativas de login fica guardado em memória, o que basta em desenvolvimento, mas em produção com vários processos precisa de um armazenamento partilhado, como o README já indica. A IA nunca acrescenta uma rota à lista de rotas públicas sem uma decisão da equipa.

Dados e base de dados

A base de dados é onde um erro custa mais a corrigir. Por isso, as alterações seguem regras próprias, que o projeto em parte já cumpre.

O esquema ativo é o de app/models.py e de migrations/. O database/schema.sql é igual ao modelo de referência v2 e já não coincide com a base (não tem, por exemplo, a tabela das zonas); como diz o README, nunca se aplica à base. A aplicação liga como app_user, que só lê e escreve dados, e as migrações correm como app_owner. Os testes usam uma base própria, com nome terminado em _test, criada e apagada em cada execução.

Migração Conteúdo

923e45090da8 Alterações aos imóveis e aos valores monetários

Uma migração nova, gerada pelo Flask-Migrate ou proposta pela IA, é lida e testada com upgrade e downgrade numa base de teste antes de ser aplicada. Até hoje isto não é testado automaticamente, porque os testes criam as tabelas diretamente a partir dos modelos.

Os dados de teste e de demonstração estão em database/seeds/ (contactos, leads, origens de leads, oportunidades, fases e imóveis). Os nomes das fases no seed estão em minúsculas, sem acentos e com uma gralha ("em preparcao para venda"). O frontend usa "Em preparação para venda", por isso os nomes vão deixar de coincidir quando as fases passarem a vir da API. Há ainda duas coisas que só existem no modelo. O nível de acesso do utilizador é um texto sem restrição na base de dados, e só a linha de comandos garante que é owner ou investor. A tabela de auditoria existe, mas nenhum código escreve nela.

Os riscos têm uma causa comum: falta de verificação. Em todos os casos que já aconteceram havia um teste, um documento ou um build que ninguém confirmou depois de uma alteração. Lições do caso Army Crew

O caso Army Crew ajuda a explicar porque é que este handbook avalia o trabalho da equipa e não o de cada pessoa isoladamente.

Em 2002, o treinador da equipa de remo de West Point pôs no barco Varsity os oito remadores com os melhores resultados individuais. Mesmo assim, o barco Junior Varsity, com os oito piores, ganhava-lhe cerca de dois terços das vezes. Em pares ou grupos de quatro e seis, os remadores do Varsity venciam sempre, mas com os oito juntos perdiam. O Varsity não tinha nenhum líder e tinha vários elementos que criticavam os colegas individualmente, enquanto o JV corrigia os erros em conjunto e confiava que cada um recuperava a remada seguinte. No ImoVentures o risco é parecido: a IA deixa cada pessoa produzir mais código, mais depressa, mas isso não garante que as partes encaixem. O revert a25a83f e os testes de imóveis a falhar na integração mostram isso mesmo. Por isso, o progresso mede-se pelo que passa os testes na main, e não por quantos commits ou linhas cada pessoa gerou. A revisão dos PRs comenta o código e não quem o escreveu, e as críticas ao trabalho de alguém vão para o responsável da área ou para a Inês, tal como o treinador pedia que lhe fossem dirigidas a ele. Cada área tem um responsável com papel de liderança, que é precisamente o que faltava ao Varsity.

O que mudou depois do Evento 1

O cliente pediu agentes de IA que melhorem a gestão do projeto e a qualidade do produto. Até aqui o handbook tratava a IA apenas como um assistente usado a pedido. Passa a prever dois agentes automáticos, escolhidos por causa de problemas que encontrámos no repositório. Um agente de qualidade corre em cada PR: executa pytest, npm test, typecheck e build em Linux e verifica as regras de frontend/prompt.md. Teria detetado o problema do Tsconfig.json e os 53 testes de imóveis a falhar. Um agente de estado corre uma vez por semana, antes da reunião: compara o README e os docs/ com o código e lista as páginas que ainda usam dados de exemplo e os ramos por integrar. Assim, a reunião semanal parte de um estado verificado pelo agente.

Por isso, mudam as regras de utilização da IA, o workflow e as responsabilidades. Os agentes podem ler o repositório, correr testes numa base _test e comentar, mas não fazem merge, não aplicam migrações e não leem o .env. Um PR só segue para revisão humana depois de o agente de qualidade passar, e cada agente tem um dono na tabela de responsabilidades. Os agentes ainda não estão implementados. A ferramenta está por decidir (o repositório está no GitHub, por isso GitHub Actions é a opção óbvia). Falta também confirmar com o cliente se queria agentes no processo de desenvolvimento, como aqui se assume, ou dentro do próprio CRM.

O exemplo mais detalhado é o cálculo do retorno líquido do investidor (commit 665ff89, tarefa 09). O cliente calcula numa folha de cálculo quanto recebe um investidor depois de impostos: uma empresa paga IRC de 19% (0% com CAEP superior a 1 ano) e um particular paga IRS de 28%. O Claude escreveu o frontend/src/lib/taxRules.ts (59 linhas), os testes em frontend/tests/taxRules.test.ts (42 linhas) e o comando npm test. Os testes exigem os valores da folha do cliente ao cêntimo, para um lucro de 47 037,39 €, um capital de 231 700 € e um prazo de 6 meses:

Investidor CAEP Taxa Lucro líquido Cash-on-cash Anualizado
Empresa Mais de 1 ano 0% 47 037,39 € 20,3% 40,6%
Empresa Menos de 1 ano 19% 38 100,28 € 16,4% 32,9%
Particular Menos de 1 ano 28% 33 866,92 € 14,6% 29,2%

O código faz as contas em cêntimos e corta o resultado como a folha do cliente (38 100,2859 fica 38 100,28, quando um arredondamento normal daria 38 100,29). A folha não diz que taxa paga um particular com CAEP superior a 1 ano, por isso o código usa o IRS por defeito e deixa um TODO: confirmar com o cliente. Os limites também ficam escritos no ficheiro: só se aplicam as três taxas da folha, sem derramas, tributação autónoma nem englobamento. Foram os primeiros testes automáticos do frontend e correm com o executor de testes do Node, sem bibliotecas novas. Na verificação de 24/11/2026, os 6 testes passaram.

O que mudou depois do Evento 2

O cliente pediu evidência real do uso de LLMs para os auditores, e o handbook passou a incluí-la na secção "Evidência de utilização de LLMs", com três exemplos tirados do histórico do Git e os comandos para os confirmar. Ao reunir essa evidência, vimos que os prompts exatos de cada tarefa não estavam guardados no repositório, por isso as regras de utilização da IA passaram a exigir a marca de coautoria em cada commit feito com um LLM e o registo do prompt, do modelo e da data de cada tarefa. A tabela de responsabilidades deixou de ter papéis genéricos e passou a ter a equipa real, com o nome, o número, o e-mail e a função de cada pessoa, e com o responsável de cada área identificado.

Resposta à falha de segurança das ferramentas de IA

A equipa foi informada de que todas as ferramentas de IA que usa têm uma falha grave de segurança, incluindo as de desenvolvimento de código. Isto abrange o Claude e o GitHub Copilot, as duas ferramentas registadas no histórico do Git. A resposta tem quatro partes.

A primeira é parar. A partir de 24/11/2026 ninguém usa ferramentas de IA no projeto, seja para código, documentação ou prompts, e as extensões de IA dos editores ficam desligadas. Os agentes propostos no Evento 1 também ficam suspensos, porque dependiam destas ferramentas. A parte que não usa IA mantém-se: correr pytest, npm test, typecheck e build em cada PR pode ser um script normal de integração contínua, sem nenhum LLM.

A segunda é tratar os segredos como expostos. As ferramentas podem ter tido acesso ao repositório e aos ficheiros abertos no editor, por isso mudam-se todos os segredos do .env: SECRET_KEY, POSTGRES_ADMIN_PASSWORD, APP_OWNER_PASSWORD e APP_USER_PASSWORD. Os tokens de acesso ao GitHub que as ferramentas usaram são revogados.

A terceira é rever o código escrito com IA. O Git identifica 10 commits:

Pode haver código escrito com IA em commits sem a marca de coautoria. Por isso, cada responsável de área confirma com a sua equipa que commits foram feitos com IA e acrescenta-os à revisão.

Plano de entrega em 15 dias

O cliente quer o produto entregue em 15 dias, a 09/12/2026, com a mesma equipa de 11 pessoas e sem ferramentas de IA. Com o prazo e as pessoas fixos, a única variável que sobra é o âmbito, porque a qualidade não se corta num produto que guarda dados pessoais e financeiros.
